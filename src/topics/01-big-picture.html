התמונה הגדולה — מה הפרויקט עושה

בקצרה
  • 4 שכבות: React → nginx → Flask API → MySQL. בנפרד יש worker, תהליך Python שמקדם משפטים.
  • ה־API וה־worker לא מדברים ישירות. MySQL הוא המצב המשותף היחיד, גם להתראות החיות.
  • הגשת תביעה = ה־API כותב שורה עם סטטוס ו־deadline. את כל השאר עושה ה־worker כשה־deadline עובר.
  • 31 בוטים (20 מושבעים, 8 שופטים, 3 מנחי תוכן). מה שהם אומרים בא מה־brain: offline או LLM.

LolSuit היא רשת חברתית סאטירית בעברית: משתמשים מגישים "תביעות" מצחיקות (נגד אדם רשום או נגד משהו מופשט כמו "יום שני"), וכל תביעה עוברת משפט אמיתי: זימון עדים, חבר מושבעים של 7 בוטים עם אישיות, ושופט שפוסק. 31 בוטים (20 מושבעים, 8 שופטים, 3 מנחי תוכן) גם מגיבים, עושים לייק, עונים להודעות ותובעים זה את זה.

רעיון מרכזי — 4 שכבות, 2 תהליכי Python, מצב משותף אחד

Frontend (React) ← nginx ← API (Flask תחת gunicorn) ← MySQL. ובנפרד: worker — תהליך Python נפרד (לא thread!) שמקדם משפטים כל 15 שניות. ה־API וה־worker לא מדברים זה עם זה ישירות; MySQL הוא המצב המשותף היחיד — כולל "אוטובוס" ההתראות החיות (SSE הוא cursor על notifications.id).

שלוש החלטות שכדאי לדעת לומר בעל־פה

  1. create_app() בלי תופעות לוואי (server/app/__init__.py:23) — לא יוצרת סכמה ולא עושה seed, כך שכמה gunicorn workers עולים במקביל בלי מרוץ על יצירת טבלאות. הסכמה מגיעה מ־init.sql דרך ה־entrypoint של MySQL, וה־seed הוא תהליך נפרד.
  2. ה־worker הוא תהליך נפרד, לא thread — thread בתוך gunicorn היה "מתקתק" פעם אחת לכל worker process, וכל משפט היה מתקדם פעמיים־שלוש. בטוח להריץ כמה: GET_LOCK ליעילות, ו־FOR UPDATE SKIP LOCKED + UPDATE מותנה־סטטוס לנכונות.
  3. שעון אחד — של MySQL: כל deadline נכתב ונבדק עם UTC_TIMESTAMP(), כך שה־API וה־worker לעולם לא חלוקים על "האם השלב נגמר".
טיפ למבחן אם שואלים "מה קורה כשמגישים תביעה?" — התשובה הקצרה: ה־API רק כותב שורה עם status='witness_phase' ו־phase_deadline_at. כל השאר (חבר מושבעים, הצבעות, פסק דין, סגירה) נעשה ע"י ה־worker כשה־deadline עובר.
