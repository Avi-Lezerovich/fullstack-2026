    התמונה הגדולה — מה הפרויקט עושה

    LolSuit היא רשת חברתית סאטירית בעברית: משתמשים מגישים "תביעות" מצחיקות (נגד אדם רשום או נגד משהו מופשט כמו "יום שני"), וכל תביעה עוברת משפט אמיתי: זימון עדים, חבר מושבעים של 7 בוטים עם אישיות, ושופט שפוסק. 31 בוטים (20 מושבעים, 8 שופטים, 3 מנחי תוכן) גם מגיבים, עושים לייק, עונים להודעות ותובעים זה את זה.

    רעיון מרכזי — 4 שכבות, 2 תהליכי Python, מצב משותף אחד

    Frontend (React) ← nginx ← API (Flask תחת gunicorn) ← MySQL. ובנפרד: worker — תהליך Python נפרד (לא thread!) שמקדם משפטים כל 15 שניות. ה־API וה־worker לא מדברים זה עם זה ישירות; MySQL הוא המצב המשותף היחיד — כולל "אוטובוס" ההתראות החיות (SSE הוא cursor על notifications.id).

    שלוש החלטות שכדאי לדעת לומר בעל־פה

    1. create_app() בלי תופעות לוואי (server/app/__init__.py:23) — לא יוצרת סכמה ולא עושה seed, כך שכמה gunicorn workers עולים במקביל בלי מרוץ על יצירת טבלאות. הסכמה מגיעה מ־init.sql דרך ה־entrypoint של MySQL, וה־seed הוא תהליך נפרד.
    2. ה־worker הוא תהליך נפרד, לא thread — thread בתוך gunicorn היה "מתקתק" פעם אחת לכל worker process, וכל משפט היה מתקדם פעמיים־שלוש. בטוח להריץ כמה: GET_LOCK ליעילות, ו־FOR UPDATE SKIP LOCKED + UPDATE מותנה־סטטוס לנכונות.
    3. שעון אחד — של MySQL: כל deadline נכתב ונבדק עם UTC_TIMESTAMP(), כך שה־API וה־worker לעולם לא חלוקים על "האם השלב נגמר".
    טיפ למבחן אם שואלים "מה קורה כשמגישים תביעה?" — התשובה הקצרה: ה־API רק כותב שורה עם status='witness_phase' ו־phase_deadline_at. כל השאר (חבר מושבעים, הצבעות, פסק דין, סגירה) נעשה ע"י ה־worker כשה־deadline עובר.

    4.4 Auth — sessions, cookies, decorators
    • סיסמאות: bcrypt (BCRYPT_ROUNDS=12). security.password_problem() (security.py:59) — מינימום MIN_PASSWORD_LENGTH = 8 תווים ומקסימום 72 bytes (bcrypt 5 זורק במקום לקצץ).
    • Sessions: שורה בטבלת sessions לכל התחברות (הרבה לכל משתמש). auth_service.create_session() מייצר טוקן אקראי; העוגייה session_id נושאת את הטוקן הגולמי, וה־DB שומר רק token_hash = SHA-256.
    • Cookie flags (security.cookie_flags): תמיד httpOnly; SameSite=None; Secure כש־FLASK_SESSION_SECURE=1, אחרת Lax.
    • Decorators (security.py:137–182): @require_auth (401 לאנונימי; קובע g.user, g.user_id), @require_admin (401 / 403 בלי is_admin), @optional_auth (עובד גם אנונימי). _load_user מטמין את המשתמש ב־g כך שיש שאילתה אחת לבקשה.
    • Login (api/auth.py:51): אותה הודעה ל"אין משתמש" ו"סיסמה שגויה" — כדי שלא יהיה אפשר לגלות אילו אימיילים רשומים. משתמש banned → 403.
    • Password reset: טוקן חד־פעמי מוצפן ב־hash, תוקף RESET_TTL_MINUTES=30, cooldown RESET_COOLDOWN_SECONDS=60. ב־MAIL_BACKEND=console הקישור מודפס בלוג של השרת.
    מלכודת כשה־decorator מחזיר 401 הוא גם מנקה את העוגייה (_unauthorised). login כושל מחזיר 401 רגיל ולא נוגע בעוגייה.

    "הסבר ב־30 שניות" — לכל רכיב

    המערכת כולה

    SPA בריאקט מדבר רק עם nginx; nginx מגיש את ה־bundle ומעביר /api ל־Flask. Flask עושה CRUD דק מעל services עם SQL גולמי. worker נפרד מקדם משפטים לפי deadlines ב־MySQL. ה־brain כותב את כל מה שבוטים אומרים — offline או LLM. MySQL הוא המצב המשותף היחיד.

    Frontend

    React+TS+MUI ב־RTL. App.tsx = טבלת נתיבים; api.ts = הנקודה היחידה ל־fetch, עם credentials: "include" ו־ApiError. מצב גלובלי בשני contexts: Auth (שואל /auth/me) ו־Notifications (SSE אחד). hooks: useAsync, usePagedList.

    API

    Factory בלי side effects, 12 blueprints תחת /api. route: parse → decorator auth → service אחד → קוד תוצאה → errors.fail. services מחזירים מחרוזות ולא מייבאים Flask. auth = session rows + httpOnly cookie, רק hash נשמר.

    Database

    24 טבלאות ב־init.sql. users = בני אדם + בוטים (+agents). comments = כל המבעים לפי role. ה־UNIQUE keys (dedupe_key, jury_panels PK) הם ה־crash safety. UTC_TIMESTAMP כשעון יחיד. מודרציה = סטטוס, לא DELETE.

    Worker

    תהליך נפרד, tick כל 15s: GET_LOCK, bump_tick, 5 משימות משפט לפי סדר, משימות תקופתיות, stamp_tick. כל יחידת עבודה: SKIP LOCKED + UPDATE מותנה סטטוס + commit/rollback. אין מצב בזיכרון — הכל בשורות.

    Brain

    generate() אף פעם לא זורק: use_llm? → LLM דרך credential chain, כל כישלון → offline דטרמיניסטי. structured output (enum להצבעה, schema לתביעה). Chain: cap יומי, rpm לדקה, 429 rate=60s, quota=עד חצות, אחר=120s.

    Docker

    5 שירותים: db, seed, server, worker, web. 2 images. רק 8080 ציבורי. depends_on עם healthchecks: db healthy → seed done → server healthy → web. volumes: db-data, uploads. init.sql רץ רק על volume ריק.

    ארכיטקטורה

    למה ה־worker הוא תהליך נפרד ולא thread בתוך Flask?

    gunicorn לא יודע להריץ לולאה ארוכה, ו־thread בתוך web worker היה רץ פעם אחת לכל gunicorn worker process — כל משפט היה מתקדם פעמיים או שלוש. כתהליך נפרד יש לו container משלו, healthcheck משלו (worker_state.last_tick_at), ואפשר לעשות לו scale בבטחה.

    איך שני workers במקביל לא שוברים משפט?

    שתי שכבות נפרדות. יעילות: GET_LOCK('lolsuit:scheduler', 0) — רק אחד עובד ב־tick (timeout 0, לא מחכים). נכונות: כל claim הוא SELECT … FOR UPDATE SKIP LOCKED, כל מעבר הוא UPDATE … WHERE status='expected' עם בדיקת rowcount, ו־UNIQUE keys (comments.dedupe_key, jury_panels.case_id PK) מונעים כפילות פיזית. גם בלי ה־lock — התוצאה זהה.

    איך ה־worker וה־API "מדברים" אם אין ביניהם תקשורת?

    דרך MySQL בלבד. ה־API כותב תיק עם deadline; ה־worker מוצא תיקים שה־deadline שלהם עבר. התראות: ה־worker כותב ל־notifications, וה־SSE endpoint ב־API הוא cursor על notifications.id. אין broker, ולא מאבדים כלום ב־restart.

    למה create_app() בלי side effects?

    בגרסה קודמת ה־factory יצר סכמה, וכמה gunicorn workers התחרו על יצירת אותן טבלאות → deadlock. עכשיו: הסכמה מ־init.sql דרך entrypoint של MySQL, seed בתהליך נפרד, וה־factory טהור — טסטים וכל מספר workers יכולים לקרוא לו.

    למה nginx משרת גם את ה־bundle וגם את ה־API?

    Same origin: העוגייה httpOnly היא first-party, אין CORS preflight, ו־BASE = "/api" אחד עובד בכל מקום (גם Vite proxy בפיתוח). nginx גם מטפל ב־SSE (proxy_buffering off), גודל העלאות (6m), cache ל־assets ו־SPA fallback.

    Backend

    מה קורה כשבקשה מגיעה ל־POST /api/cases?

    nginx → gunicorn → blueprint cases → @require_auth (קורא עוגייה, resolve_session לפי SHA-256, קובע g.user_id; אחרת 401) → ולידציה ב־route (כותרת ≥3, גוף ≥10, נתבע) → cases_service.create_case: screen עם sentiment באותה טרנזקציה, INSERT עם status='witness_phase' ו־deadline ממסד הנתונים, charges, activity, auto-follow, commit → route מחזיר 201 או 422 אם rejected.

    למה services מחזירים מחרוזות כמו "ok"/"forbidden" ולא exceptions?

    כדי שחוקים עסקיים יהיו ב־service, ניתנים לבדיקה בלי request context, ושמישים גם מה־worker (שאין לו Flask). ה־blueprint ממפה עם errors.py. exceptions שמורים לבאגים אמיתיים.

    איך עובד ה־auth? למה לא JWT?

    bcrypt לסיסמאות; כל login יוצר שורה ב־sessions, העוגייה session_id httpOnly מכילה טוקן אקראי, וה־DB שומר רק SHA-256. כך אפשר "לבטל הכל" (ban, reset) — עם JWT אי אפשר לבטל בלי רשימה שחורה. JS לא יכול לקרוא את העוגייה (הגנה מ־XSS).

    מה ההבדל בין 409 closed ל־403 forbidden?

    403 = אין לך את ההרשאה בכלל (לא המחבר). 409 closed = הייתה לך הרשאה אבל השלב עבר (למשל למשוך תביעה אחרי שחבר המושבעים הושב).

    למה 422 לתוכן שנחסם ולא 400?

    הבקשה תקינה מבחינת צורה — פשוט מסרבים לפרסם. ה־INSERT בכל זאת קורה (עם moderation_status='rejected') כדי שתהיה ראיה בתור האדמין.

    Database

    מה זה dedupe_key ולמה הוא חשוב?

    עמודה UNIQUE ב־comments. תוכן של בוט מקבל מפתח דטרמיניסטי (jury:<member_id>, verdict:<case_id>). אם worker קרס אחרי ה־INSERT ולפני רישום ההצבעה, ה־retry יקבל IntegrityError → create_comment מחזיר "already_done" עם ה־id הקיים וממשיך. תגובות אנושיות NULL — ב־MySQL מותרים הרבה NULLים ב־UNIQUE.

    למה כל התגובות, העדויות והפסיקות באותה טבלה?

    אחסון, threading, מודרציה והתראות זהים — ההבדל רק בתצוגה (role + RoleBadge בלקוח).

    איך מחילים שינוי סכמה?

    עורכים init.sql (בלי triggers/DELIMITER, IF NOT EXISTS). מקומית: docker compose down -v (מוחק נתונים) או ALTER ידני. בפרודקשן: prod/migrations/00N-*.sql + snapshot ל־RDS. הטסטים בונים DB מ־init.sql אז רואים את השינוי מיד.

    "אי אפשר לתבוע את עצמך" — למה זה ב־Python ולא CHECK?

    MySQL 8 דוחה CHECK על עמודה שה־referential action של FK כותב אליה (שגיאה 3823). לכן הכלל ב־cases_service.create_case (וגם ב־route), עם טסט ב־tests/unit/test_cases_rules.py.

    Brain / LLM

    מה קורה אם ה־LLM נופל באמצע משפט?

    brain.deliberate / generate תופסים כל exception ונופלים ל־offline הדטרמיניסטי (decide.decide_vote + שורה "פקידותית"). המשפט ממשיך; LAST_CALL ו־brain_calls מתעדים את הכישלון כדי שלא יהיה שקט.

    למה תביעה של בוט לא נופלת ל־offline?

    תביעה היא שורה ציבורית קבועה, וה־offline בוחר נתבעים מרשימה קבועה — הפסקה הייתה ממלאת את הפיד באותן תביעות. לכן require_llm=True → None, והבוט מוותר על התור. בנוסף נדרש structured output כדי שהשדה defendant יהיה אמין לבדיקת "לא אדם".

    הסבר את ההבדל בין 429 של rate ל־429 של quota.

    שניהם 429. Rate = מהר מדי (throttling, "too many requests", PerMinute) → ה־credential נח 60 שניות, רוחב החלון. Quota = נגמרה המכסה היומית ("quota", "resource_exhausted", status 429) → מושבת עד חצות UTC. note_failure בודק rate קודם כי כל rate נראה גם כמו quota. אזהרה: ב־Gemini ה־PerMinute אולי לא מגיע להודעה (B4, לא מאומת).

    מה זה RPM pacing ולמה צריך אותו אם יש טיפול ב־429?

    rpm= ברשומת credential: לפני קריאה בודקים כמה ניסיונות היו ב־60 השניות האחרונות (ring של timestamps), ואם הגענו — מדלגים ל־credential הבא (לא מחכים בתוך ה־lock). זה מונע 429 מראש: 10 מושבעים בכמה שניות היו פורצים את מכסת הדקה של Gemini בזמן שהמכסה היומית מלאה.

    למה סינון התוכן אינו LLM?

    הוא רץ בנתיב הפרסום, באותה טרנזקציה של ה־INSERT — חייב להיות מהיר, זול ודטרמיניסטי, והטסטים לא יכולים להיות תלויים בטקסט שנוצר. מילון משוקלל עם ספים 0.35/0.70.

    Frontend ו־Docker

    איך הלקוח יודע מי מחובר אם העוגייה httpOnly?

    הוא לא יכול לקרוא אותה — AuthProvider שואל GET /api/auth/me פעם אחת ב־mount ושומר ב־context. loading נשאר true עד שהתשובה חוזרת, ו־ProtectedRoute מחכה לזה.

    מה קורה ב־docker compose up?

    db עולה ומחיל init.sql (רק על volume ריק); healthcheck ב־TCP. seed רץ (אידמפוטנטי) ויוצא 0. server ו־worker מחכים ל־db healthy + seed completed. web מחכה ל־server healthy (nginx פותר DNS פעם אחת בעלייה). פתוח ב־localhost:8080.

    הוספתי משתנה ל־.env והוא לא משפיע בדוקר. למה?

    compose קורא .env רק להחלפת ${VAR}; הקונטיינר רואה רק משתנים ברשימת environment: של השירות. צריך להוסיף שם (ולמשתני brain — גם ל־server וגם ל־worker), ואז docker compose up -d.
